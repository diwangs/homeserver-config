# prydwen OpenWrt role

This role reconciles the router configuration captured from prydwen using
the shell-based community.openwrt collection. It supports OpenWrt 25.12.x
targets using APK and does not require Python on the router.

For an already-configured router, run:

~~~sh
ansible-galaxy collection install -r requirements.yml
ansible-playbook playbooks/configure.yml --limit prydwen --check --diff
ansible-playbook playbooks/configure.yml --limit prydwen
~~~

For a fresh OpenWrt installation, connect its WAN side to a network with
package-repository access, connect through its factory management address,
and run:

~~~sh
ansible-playbook playbooks/init_openwrt.yml \
  -e openwrt_bootstrap_host=192.168.1.1
~~~

The bootstrap play installs packages and authentication first, stages network
state last, then reconnects to the final inventory address. Ensure a private key
matching one of managed_authorized_keys is available before applying: that list
becomes the router's complete set of authorized keys. Ansible itself uses the
automation key at .ssh/sentinel-lp-ansible (ansible.cfg private_key_file).

Hardware portability is provided by host_vars/prydwen.yml: physical devices,
VLAN devices, bridges, and logical interfaces are data rather than hard-coded
role tasks. A different router should override those lists while retaining the
logical DHCP, firewall, DNS, and service declarations it needs.

The vaulted variables vault_openwrt_cloudflare_api_token,
vault_openwrt_root_password, and vault_openwrt_root_password_hash live in the
existing encrypted group vault. Device SSH host keys, uHTTPd certificates, and
Tor identities are intentionally generated by each router.

End hosts own DSCP classification. The managed `lan-qos` init service installs
unlimited-rate CAKE diffserv4 queues directly on the physical lan1 and lan3
trunks, preserving client DSCP without an additional packet classifier. The
existing SQM instance continues to manage WAN bufferbloat on lan0. Because the
LAN queues are deliberately unshaped, priority takes effect only while the
kernel queue itself has a backlog; it does not move a downstream bottleneck
into the router.

## How changes are applied

Day-to-day runs (`playbooks/configure.yml`) apply changes the way LuCI's
"Save & Apply" does, not by restarting everything. Each UCI task commits its change
and records which config package it touched; a handler then sends procd one
`config.change` event per changed package (`ubus call service event`). procd reloads
only the services with a reload trigger for that package — dnsmasq/odhcpd for
`dhcp`, fw4 for `firewall`, netifd for `network` (which reconfigures only the
interfaces whose settings changed), and so on. A DHCP-only change therefore never
takes interfaces down or reconnects the WAN.

The exceptions are explicit:

- `tor` registers no reload trigger, so a `tor`/`tor-hs` change restarts it.
- A changed `setupjool.sh` re-runs it (it recreates the Jool namespace).
- A changed `lan-qos` init script restarts `lan-qos`.
- Router SSH keys and the root password apply on the next login; nothing restarts.

First-run provisioning (`playbooks/init_openwrt.yml`) still restarts networking and
services outright in its finalize stage.
